# lazycogs: reprojection semantics relative to the GDAL warp API, and the xarray interface relative to odc

An assessment of [developmentseed/lazycogs](https://github.com/developmentseed/lazycogs) v0.7.0 (source read in full), with the reprojection machinery compared point by point against the GDAL warp API, and the xarray user experience contrasted with odc-stac/odc-geo. Claims about pixel-level behavior below were verified empirically against GDAL 3.8.4, rasterio 1.5.0, odc-stac 0.5.3 and lazycogs 0.7.0; the experiments are described in the appendix and the accompanying `scripts/` directory reproduces the comparison on real Sentinel-2 data on AWS.

## 1. What lazycogs is

lazycogs takes the pattern established by stackstac and odc-stac - a STAC item set exposed as a spatially aligned, lazy xarray array - and rebuilds it with no GDAL anywhere in the stack. STAC discovery is a DuckDB query over stac-geoparquet (rustac), COG access is a Rust async reader (async-geotiff) over obstore, and reprojection is pyproj plus numpy indexing. The result of `lazycogs.open()` is a lazy `(band, time, y, x)` DataArray whose every chunk read triggers its own targeted spatial/temporal query against the parquet index, reads only the COG windows that intersect that chunk, warps them onto the destination grid, and mosaics them with a pixel-selection method.

Three design decisions do most of the work of differentiating it:

First, the item index is never loaded into memory. stackstac and odc-stac both require the full list of items up front (a STAC API search, then a Python list of pystac items) and build a task graph over it; `open()` in lazycogs runs one representative-item inspection plus one datetime-column scan and returns immediately, so array construction cost is roughly constant in archive size. Discovery is deferred to compute time, per chunk.

Second, compositing is a load-time concept, not a post-hoc reduction. The time axis is defined by a temporal grouping (`P1D` by default, up to `P1Y`, or hour buckets), and each time step is materialized by feeding overlapping items through a mosaic method (`First`, `Mean`, `Median`, etc., ported from rio-tiler). A monthly median composite is therefore a property of the array you open, not a `groupby("time.month").median()` over a much larger daily array. The default `FirstMethod` can stop reading further items as soon as every output pixel is filled, which is an I/O optimization no graph-based loader expresses naturally.

Third, everything is async on one shared event loop, with reads for all bands of an item issued concurrently and a bounded thread pool for the CPU-bound warp work. Dask is optional and only spatial/temporal chunking makes it involved at all.

The constraint that buys all of this: input must be COGs, and the only resampling on offer is nearest neighbour.

## 2. The reprojection path, and how it relates to the GDAL warp API

### 2.1 What lazycogs actually implements

The whole warp lives in `_reproject.py` (181 lines) plus window/overview planning in `_chunk_reader.py`. Per source read it is an inverse-mapping sampler, structured exactly like the inner loop of a warp kernel:

1. Build the destination pixel-centre grid: `x = c + (col + 0.5) * a`, `y = f + (row + 0.5) * e` from the chunk affine.
2. Transform every centre from destination CRS to source CRS in one vectorized `pyproj.Transformer.transform` call (transformer objects cached per CRS pair).
3. Map through the inverse of the source window affine to fractional pixel coordinates, then `floor` to integer source indices - i.e. the sample is the source pixel that geometrically contains the transformed destination centre.
4. Gather with numpy fancy indexing; destination pixels whose indices fall outside the source window are filled with nodata (or 0).

The resulting `WarpMap` (integer row/col index arrays at destination shape) is cached keyed on `(window transform, source CRS)`, so every band and every time step whose read window has identical geometry - the common case for tiled collections like Sentinel-2, where a chunk cuts the same window from hundreds of scenes on the same MGRS grid - reuses one map. There is also a paste fast path: when source CRS, window transform and dimensions match the destination chunk exactly, pixels are passed through untouched.

Around this kernel sits the read planning: the chunk bbox is projected to the source CRS (four corners, axis-aligned envelope), mapped through the inverse source affine, clamped, and becomes the read window; overview selection picks the coarsest overview whose pixel size (in source CRS units, estimated by projecting two adjacent destination pixel centres at the chunk centre) is still no larger than the target pixel size, falling back to full resolution rather than ever upsampling from an overview.

### 2.2 Correspondence with the GDAL warp model

It is worth being precise about what "the GDAL warp API" is: a destination-driven engine (`GDALWarpOperation` + `GDALWarpKernel`) that for each destination block computes the corresponding source window, runs a transformer chain (pixel/line -> georeferenced -> pixel/line, optionally wrapped in an approximating transformer), and evaluates a resampling kernel per destination pixel, with band masks, density/alpha blending, working data types, memory-bounded block iteration and multithreading around it.

lazycogs implements a small, exact subset of this model, and the correspondence is close enough to name term by term. Its `compute_warp_map` is GDAL's inverse transformer step evaluated at every destination pixel centre; its `floor` gather is precisely GDAL's nearest-neighbour convention (GDAL's NN kernel also selects the source pixel containing the transformed coordinate); its window computation mirrors `GDALWarpOperation`'s source-window estimation (corner projection plus clamp - GDAL additionally samples along edges and adds safety margins, which matters for strongly curved transforms); its per-chunk execution corresponds to GDAL's per-block iteration, except memory is bounded by xarray/dask chunking rather than `dfWarpMemoryLimit`; its reprojection thread pool corresponds to `NUM_THREADS`, though GDAL parallelizes within one warp while lazycogs parallelizes across item reads and runs each warp single-threaded.

The differences that matter:

**Transformer approximation.** GDAL's warp, as driven by `gdalwarp` and by `rasterio.warp.reproject`, does not by default transform every destination pixel exactly. It wraps the projection in `GDALApproxTransformer` with an error threshold of 0.125 source pixels, transforming scanline endpoints and interpolating linearly in between, subdividing where the error exceeds threshold. lazycogs has no approximation: every pixel centre goes through the full PROJ pipeline. Two consequences, both verified here: (a) with the approximation disabled (`gdalwarp -et 0`, or rasterio `tolerance=0`), lazycogs' nearest-neighbour output is bit-identical to GDAL's - same grid, same pixel selection, same edges; (b) with GDAL defaults, nearest-neighbour pixel choice flips wherever the approximation error moves a sample across a source-cell boundary - in a UTM 55S -> Australian Albers warp of 10 m data to 30 m this affected 3.8 percent of pixels (appendix, experiment 1). This is the single largest source of lazycogs-vs-odc result differences in practice, and it is GDAL's approximation, not lazycogs, that deviates from the exact answer. The flip side is cost: the approximate transformer is the reason gdalwarp's geometry stage is cheap, whereas lazycogs pays full PROJ cost per destination pixel - and then amortizes it aggressively via the warp-map cache, which GDAL has no equivalent of (each GDAL warp operation recomputes its transform sampling; nothing is shared across scenes or bands read in separate operations).

**Resampling.** GDAL offers nearest, bilinear, cubic, cubicspline, lanczos, average, mode, rms, min/max/med/q1/q3/sum, each with correct kernel-support windows, source-density handling and (for the statistical methods) area-weighted semantics. lazycogs offers nearest neighbour, full stop. For categorical rasters, masks, and integer spectral data being mosaicked at native-or-coarser resolution this is defensible (and byte-preserving); for continuous fields at changed resolution it is a real limitation - there is no anti-aliased downsampling (GDAL `average` at 10x reduction vs lazycogs NN through an overview ladder are different estimators), and no interpolated upsampling. A design spec in the repo (`dev-docs/specs/resampling-methods.md`) lays out bilinear/cubic via the `interpn` Rust library, including the kernel-radius halo needed in both the read window and the STAC search bbox - the analysis in that spec is sound, but as of 0.7.0 none of it is implemented.

**Georeferencing models.** GDAL's transformer chain handles GCP polynomials, thin-plate splines, RPCs, and geolocation arrays; lazycogs supports affine georeferencing only - which is what COGs in cloud archives have, so within its stated scope this costs nothing.

**Masking and nodata.** GDAL warp carries per-band mask semantics, alpha bands, `UNIFIED_SRC_NODATA`, cutlines, and blend distances. lazycogs has a single scalar nodata contract per array (inferred from a representative item or supplied explicitly; mixed-sentinel collections are rejected rather than silently unified), and its mask rule for mosaicking is that a pixel is masked only where all bands of that item read equal nodata - closer to `UNIFIED_SRC_NODATA=NO`... actually closer to unified-any-valid: one valid band keeps the position unmasked for the item. No cutlines, no alpha, no partial-density blending; edges are hard.

**Edge cases.** GDAL carries two decades of special-casing for antimeridian-crossing sources, polar projections, and transform failures. lazycogs' corner-envelope window computation and unchecked `transformer.transform` will be wrong or degenerate in some of those configurations (a UTM chunk straddling the antimeridian against a geographic source, for instance, produces a world-spanning envelope). For mid-latitude continental workflows this rarely surfaces, but gdalwarp is the tool with the guard rails.

**Overview selection.** All three engines implement "use overviews by default for decimated reads", and on exact-ratio targets they agree (appendix, experiment 2: 10 m source with 20/40/80 m overviews queried at eleven target resolutions - gdalwarp AUTO, odc's `pick_overview` and lazycogs' `_select_overview` chose identical levels at every step, all switching exactly at the overview's own resolution and never upsampling from a coarser overview). But the policies are not the same function. lazycogs compares real-valued resolutions strictly (overview res <= target res, estimated at the chunk centre); odc computes an integer shrink factor first (`int(target/native)`), which quantizes the same way; gdalwarp AUTO estimates the target ratio by sampling the actual transformer. Near integer ratios this diverges, and it diverged in our fixture: a 20 m Australian Albers target grid measures 19.75-19.87 m per pixel when projected into the source UTM zones, so lazycogs and odc both refused the 20 m overview (it would be coarser than target by a hair) and read 4x the data at 10 m, while gdalwarp's sampled estimate rounded the other way and read the 20 m overview - after which every pixel differs, because NN from full resolution and NN from a NEAREST-decimated overview are different samples. This is worth internalizing: an innocuous-looking "20 m output" request sits exactly on a policy boundary whenever the source is 10 m UTM and the target CRS is not, and the three tools can land on either side of it. gdalwarp exposes `-ovr NONE|<level>` to pin the behavior and odc has `use_overviews=False`; lazycogs currently has no user-facing override (the resampling spec proposes `overview_level=`).

**What the manual GDAL path gives you that the wrappers do not.** Driving `gdal.Warp` yourself buys the full resampling set, `-et` control, cutlines, `-tap`-style grid snapping, working-type control, and warp-memory tuning - and costs you everything the xarray front-ends do implicitly: item discovery, per-day grouping, asset-to-band bookkeeping, mosaic-order semantics (gdal.Warp with multiple sources is last-valid-wins, so emulating the wrappers' first-valid-wins means reversing your source list), nodata contract enforcement, and cube assembly. The `03_run_gdal_manual.py` script in this package is the demonstration: it is the longest of the three runners by a wide margin and every line of it is something lazycogs or odc-stac is doing for you.

### 2.3 Verified equivalence, stated plainly

For nearest-neighbour warps of affine-georeferenced COGs onto a common grid, lazycogs' reprojection is not an approximation of the GDAL warp - it is the exact computation that GDAL approximates. On the multi-zone fixture (two UTM zones, three days, two bands, nodata wedges, warped to Australian Albers), lazycogs' full pipeline output - windows, overview decisions held equal, warp, first-valid mosaic across zones, nodata handling - was bit-identical (match fraction 1.000000, zero mask disagreements) to a manual `gdal.Warp` mosaic run with `errorThreshold=0` and `overviewLevel="NONE"`. Against GDAL defaults the same comparison reads 96.8 percent, which is the approximate transformer plus the overview-boundary flip described above. Agreement with odc-stac was 96.8 percent for the same reason (odc inherits rasterio's 0.125 px default; odc pixel output was itself bit-identical to rasterio defaults).

## 3. The xarray interface, contrasted with odc

odc's model is grid-first and eager about metadata. You bring a list of pystac items; `odc.stac.load` resolves a `GeoBox` (CRS + affine + shape, with `anchor=` snapping control and the whole odc-geo geometry toolkit behind it), buckets items by `groupby` (notably `solar_day`), and returns an `xr.Dataset` with one variable per band, either materialized or as a dask graph in which each task rasterio-reads one asset and pastes or GDAL-warps it into its chunk. Everything about the source grids is knowable up front (proj extension), resampling is per-band settable to any GDAL method, nodata/dtype conventions are configurable per collection, and downstream you are in ordinary dask-xarray land: `.median("time")`, `.groupby`, rechunking, distributed clusters. odc-geo separately gives you `xr_reproject` for warping any GeoBox-carrying DataArray after load.

lazycogs' model is query-first and lazy about everything. The "item list" is a parquet file that never loads; the array you get is a single DataArray (band as a dimension, not Dataset variables), the grid is specified as bbox + resolution + CRS only (grid alignment is your job, via `align_bbox` against a known tile grid - there is no anchor/snap machinery), and temporal compositing happens inside materialization via `time_period` + `mosaic_method` rather than as an xarray reduction afterwards. Some consequences of each choice, in both directions:

Where lazycogs is ahead of odc's UX: instant open on huge archives (their published benchmark: 0.77 s vs 45 s array initialization against a large Sentinel-2 area, and no 10 s item fetch); narrow reads are proportional to the request (a point time-series materializes only the touched windows, with the DuckDB query scoped per chunk); `da.lazycogs.explain()` is a genuinely novel dry-run planner - it reports, before any pixel I/O, which items, COG windows and overview levels a given lazy view would read, optionally opening headers for exact byte ranges; native `async` loading (`await da.load_async()`) composes with event-loop applications (a tile server can await chunk reads without a thread pool); first-valid mosaic early-exit turns dense stacks into less I/O rather than more; and there is no GDAL environment-variable liturgy (`GDAL_DISABLE_READDIR_ON_OPEN`, curl allowlists, VSI caches) because obstore's defaults are already range-request-native.

Where odc is ahead: resampling choice (the moment you need bilinear DEMs or area-weighted downsampling, lazycogs is out); Dataset semantics with per-band dtype/nodata (lazycogs enforces one dtype and one nodata sentinel across all requested bands - heterogeneous band sets like reflectance+SCL must either promote or be opened twice); any GDAL-readable format vs COG-only; grid ergonomics (GeoBox algebra, `like=`, anchor snapping, native-CRS loads with `crs="utm"`); `groupby="solar_day"` (lazycogs' `P1D` is UTC calendar days, which coincides with solar day over Australia but splits scenes near the antimeridian and for late-UTC acquisition geometries); maturity of the dask story for cluster-scale work (lazycogs' shared-event-loop backend runs inside whatever dask worker calls it, but its concurrency tuning guidance is essentially single-machine); and the wider ecosystem of things that already speak GeoBox.

Interoperability turns out to be a non-issue in the pleasant direction: lazycogs attaches both `spatial:transform`-style attributes and a GDAL-order `GeoTransform` on `spatial_ref`, plus a rasterix `RasterIndex`, so its outputs round-trip into rioxarray/odc-geo tooling.

On correctness of results between the two xarray tools: for identical item sets, grids, explicit dtype/nodata, nearest resampling and matching day-grouping, expect roughly 96-97 percent identical pixels, not 100, for the two reasons established above (GDAL's approximate transformer in odc's read path; overview-policy edge cases near integer ratios). Neither tool is "wrong" - lazycogs is the exact transform, odc is GDAL's default tolerance - but anyone diffing outputs should know the discrepancy is structural, bounded, and explainable, and that it collapses to zero only when the grids align so both take the paste path, or when comparing against GDAL run with `-et 0` and pinned overviews.

## 4. Performance expectations for the comparison harness

The `scripts/` directory runs the same task three ways against Sentinel-2 C1 L2A on AWS (earth-search STAC + sentinel-cogs bucket): one month over an AOI straddling the UTM 54/55 boundary west of Melbourne, loaded to a common 20 m EPSG:3577 grid as a `(band, time, y, x)` cube with per-day first-valid mosaics. One search feeds all three tools the identical item set (stac-geoparquet for lazycogs, the same features as JSON for odc and GDAL). Timings are phase-separated (setup/graph vs compute) and results are written to NetCDF for the pixel-level comparison in `04_compare.py`.

What I would expect the numbers to show, based on the architecture reading and the project's own published benchmarks (which compared against odc-stac 0.5.2 on similar workloads): lazycogs should win array-construction time overwhelmingly and win wall-clock on sparse access patterns (points, small windows, few time steps) and on dense stacks where FirstMethod early-exit prunes reads. odc-stac with well-chosen chunks should be competitive on full-area scans, and GDAL-manual will be dominated by per-warp HTTP setup unless VSI caching and multiplexing are tuned - its numbers are best read as "what the wrappers are saving you", not as GDAL's ceiling (a tuned VRT + warped-VRT + parallel-read pipeline can do much better, at further bookkeeping cost). Two fairness notes baked into the scripts: chunking configuration is per-tool (each library's practically recommended shape, since forcing identical chunks handicaps one or the other), and cold-vs-warm object-store caches matter more than most tool differences, so runs should be repeated and the first discarded.

## 5. Summary judgment

lazycogs is a focused, internally consistent piece of engineering with an unusually honest scope statement. Within that scope - COGs, affine grids, nearest neighbour, mosaic-and-composite workflows against large STAC archives - its reprojection is demonstrably exact GDAL-warp semantics (bit-identical under `-et 0`), its I/O planning is more parsimonious than the GDAL-based stacks, and its query-at-compute-time architecture removes the item-list scaling wall that stackstac and odc-stac share. The xarray surface has real innovations the incumbents lack: explain plans, async loading, load-time compositing with early exit.

What it is not, today, is a general warper: no resampling kernels beyond NN, no per-band contracts, no grid-snapping ergonomics, no escape hatches for the overview policy, and none of GDAL's edge-case armor. The resampling spec shows the team knows exactly where the hard parts are (kernel halos propagating into both the read window and the STAC search bbox), which is the right reason to believe the gap will narrow. For production work today the practical guidance falls out cleanly: use lazycogs where its constraints hold and its strengths bind (large archives, categorical/integer data, mosaics, composites, point/window extraction, async services); use odc where you need resampling variety, Datasets, non-COG sources, or cluster-scale dask; drop to the GDAL API when you need cutlines, exotic transforms, `average`-family downsampling, or byte-level control - and expect to write, and maintain, the bookkeeping the other two hide.

## Appendix: verified findings (local experiments)

All experiments run on GDAL 3.8.4, rasterio 1.5.0 (bundled GDAL 3.12.1), odc-stac 0.5.3/odc-geo 0.5.3, lazycogs 0.7.0, pyproj 3.7.2, Python 3.12.

**Experiment 1 - nearest-neighbour parity.** Synthetic 1200x1200 uint16 raster, 10 m, EPSG:32755, with a nodata hole, warped to a 30 m EPSG:3577 grid (324x204) by six engine configurations. Match fractions against the exact-transformer GDAL reference (`gdal.Warp`, `errorThreshold=0`):

| engine | identical pixels |
|---|---|
| gdal.Warp, errorThreshold=0 | reference |
| rasterio.warp.reproject, tolerance=0 | 100.000000 percent |
| lazycogs reproject_array (pyproj+numpy) | 100.000000 percent |
| gdal.Warp, default (et=0.125) | 96.244856 percent |
| rasterio.warp.reproject, default | 96.244856 percent |
| odc-geo xr_reproject, nearest | 96.244856 percent |

The three defaults were additionally bit-identical to each other, confirming odc's output is exactly rasterio/GDAL-default output, and that the 3.76 percent disagreement is entirely the approximate transformer.

**Experiment 2 - overview ladder policy.** 10 m COG with NEAREST overviews at 20/40/80 m, each overview overwritten with a marker value. Queried at target resolutions 10, 15, 20, 25, 30, 40, 55, 79, 80, 100, 160 m: gdalwarp AUTO, odc `pick_overview`, and lazycogs `_select_overview` chose the same level at every resolution (switch exactly at 20, 40, 80; never a coarser-than-target overview; full resolution between 10 and 20). Cross-CRS (UTM -> Albers) gdalwarp likewise picked the marker-consistent level at 20/40/80 m targets.

**Experiment 3 - end-to-end fixture parity.** Two UTM zones (32754/32755) x 3 days x 2 bands of synthetic 10 m COGs with overviews and complementary nodata wedges, indexed as stac-geoparquet, loaded to a shared 20 m EPSG:3577 grid by all three runners in this package. Results: lazycogs vs manual GDAL with `errorThreshold=0, overviewLevel="NONE"`: 1.000000 match on all pixels, zero valid-mask disagreements, across every band/day. lazycogs vs odc-stac: 0.968425. lazycogs vs GDAL defaults: 0.174714 - the low number is the overview-boundary divergence described in section 2.2 (the 20 m Albers pixel measures ~19.8 m in UTM, so lazycogs/odc read 10 m data while gdalwarp AUTO read the 20 m overview), compounding with the transformer approximation. The same comparison with overviews pinned off collapses to exact agreement, which is the recommended configuration when using the harness to validate results rather than to measure default behavior.
